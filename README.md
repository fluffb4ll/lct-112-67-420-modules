## 🚀 Быстрый старт с Docker Compose

Для запуска всей системы локально используйте эталонный `docker-compose.yml`.

### 1. Подготовка конфигурации
Скопируйте файл переменных окружения:
```bash
cp .env.example .env
```
При необходимости отредактируйте `.env` (например, измените логин/пароль администратора или параметры БД).

### 2. Запуск контейнеров
Запустите все сервисы в фоновом режиме:
```bash
docker compose up -d --build
```

При первом запуске сервис `models` один раз скачивает веса ИИ-контура в том `ai_models`
(около 1,7 ГБ: LLM Qwen2.5-1.5B GGUF, faster-whisper small, голоса Piper irina и denis).
Сайт откроется только после окончания загрузки (`docker compose logs -f models` — прогресс).
После этого всё работает без сети. Отключить докачку: `DDS_FETCH_MODELS=0`; другая LLM:
`DDS_LLM_MODEL_URL=<ссылка на .gguf>` (файл ляжет в `/models/llm/model.gguf`).

### 3. Доступ к сервисам
- **Фронтенд**: [http://localhost](http://localhost) (порт `80` по умолчанию)
- **Бэкенд API**: [http://localhost:8080](http://localhost:8080) — только с этой машины (`BACKEND_BIND=127.0.0.1`);
  фронт ходит к API через nginx
- **ИИ-сервис**: [http://localhost:8090](http://localhost:8090) — только с этой машины (`AI_BIND=127.0.0.1`)
- **База данных PostgreSQL**: `localhost:5432` — только с этой машины (`POSTGRES_BIND=127.0.0.1`)

## 📦 Скрипт сборки и публикации образов (`build-and-push`)

В репозитории заготовлены два эквивалентных скрипта для сборки и отправки (push) всех контейнеров в Docker Registry:
- `build-and-push.sh` — Bash-скрипт (Linux / macOS / CI/CD)
- `build-and-push.py` — Python-скрипт (Кроссплатформенный: Windows / Linux / macOS)

### Основные возможности скриптов:
- Автоматическая сборка образов всех трех модулей (`dds-ai`, `dds-backend`, `dds-frontend`).
- Настройка адреса Docker Registry и тегов.
- Пуш в любой реестр (Docker Hub, GitHub Container Registry `ghcr.io`, Yandex Container Registry, Docker GitLab и др.).
- Поддержка мультиплатформенной сборки `--platform linux/amd64,linux/arm64` через Docker Buildx.
- Выбор отдельных модулей для сборки.

### Варианты использования:

#### 1. Сборка и пуш в Docker Hub:
```bash
./build-and-push.sh --registry docker.io/myusername --tag v1.0.0
```
или на Python:
```bash
python3 build-and-push.py -r docker.io/myusername -t v1.0.0
```

#### 2. Сборка и пуш в GitHub Container Registry (ghcr.io):
```bash
./build-and-push.sh --registry ghcr.io/myorg --tag latest
```

#### 3. Только локальная сборка (без отправки в реестр):
```bash
./build-and-push.sh --no-push
```

#### 4. Сборка конкретного модуля (например, только backend):
```bash
./build-and-push.sh -r myregistry.com/dds -m "backend"
```

#### 5. Мультиархитектурная сборка (AMD64 + ARM64):
```bash
./build-and-push.sh -r ghcr.io/myorg --platform linux/amd64,linux/arm64
```

## 🧪 Тесты бэкенда

Бэкенд собирается и тестируется в Docker — локальная JDK не нужна. Из корня репозитория:

```bash
docker run --rm -v "$PWD/backend":/app -v lct-m2:/root/.m2 -w /app eclipse-temurin:25-jdk-alpine sh -c 'chmod +x mvnw && ./mvnw -B -q test'
```

Один класс — `-Dtest=EvaluationServiceTest`. Том `lct-m2` кэширует зависимости Maven между запусками.

Юнит-тесты сервисов (JUnit 5 + Mockito) не поднимают Spring-контекст и не требуют БД. Интеграционный `Lct11267420HttpBackendApplicationTests` (подъём контекста) без переменной `DB_URL` пропускается; чтобы прогнать его, передайте в контейнер `DB_URL`, `DB_USER`, `DB_PASSWORD` и `PEPPER` доступного PostgreSQL.

## 🤖 Что делает ИИ-контур

Всё работает локально, без облачных API.

- **Оценка сданных карточек.** Бэкенд после сдачи карточки асинхронно вызывает
  `POST /api/v1/ai/evaluate`. Правила регламента (статусы, время открытия, звонок руководителю,
  комментарий, грамотность) дают нижнюю границу балла. LLM-судья читает комментарий и доклад,
  может только поднять балл за содержание и пишет разбор. Преподаватель видит итог и разбор в
  карточке сессии, может перезапросить оценку кнопкой «Оценить ИИ заново».
- **Генерация сценариев.** «Банк сценариев → Сгенерировать»: структура и эталон строятся по
  классификатору, LLM переписывает текст (описание, ответ руководителя, эталонный доклад,
  реплики). Каждое поле проходит проверку: эталонный доклад должен проходить ту же проверку,
  что и доклад обучающегося. Иначе поле остаётся из шаблона.
- **Голос.** Софтфон пишет доклад с микрофона и распознаёт его faster-whisper (`POST /v1/stt`),
  ответы собеседника озвучивает Piper (`POST /v1/tts`, мужской и женский голос).
  Без моделей — Web Speech браузера, затем ввод доклада текстом.

Без LLM (нет файла модели) оценка и сценарии работают по правилам и шаблонам.

## 🛠️ Архитектура Compose-контейнеров

```
               +-----------------------+
               |   frontend (Nginx)    |  <-- Порт 80 (пользователь)
               +-----------+-----------+
                           | /api proxy        | /ai proxy (сценарии, голос)
                           v                   v
               +-----------------------+
               |  backend (Spring)     |  <-- Порт 8080
               +-----+-----------+-----+
                     |           |
        JDBC / 5432  v           v  HTTP / 8090
      +---------------+         +---------------+
      |   postgres    |         |   ai (Python) |
      +---------------+         +---------------+
```

### Зависимости и Healthcheck'и
- `postgres`: Ожидает готовности базы данных через `pg_isready`.
- `ai`: Предоставляет healthcheck `/health`.
- `backend`: Запускается строго после того, как `postgres` и `ai` перейдут в состояние `healthy`.
- `models`: разово докачивает веса в том `ai_models` и завершается; `ai` ждёт его завершения.
- `frontend`: Запускается после старта `backend` и проксирует `/api` запросы на `http://backend:8080`,
  а `/ai/` — на `http://ai:8090` (только после входа, см. «Безопасность демо»).

## 🔒 Безопасность демо

- **ИИ-контур за входом.** nginx фронта пускает к `/ai/` только с действующей кукой входа
  `AUTH_TOKEN`: перед каждым запросом подзапрос `auth_request` к `GET /api/auth/check`
  (204 — пускаем, 401 — нет). Наружу открыто лишь то, что зовёт фронт: `/ai/v1/voice`,
  `/ai/v1/tts`, `/ai/v1/stt` (запись до 10 МБ) и `/ai/v1/scenarios/compose`; оценка и попытки
  доступны только бэкенду по внутренней сети (и локально на `127.0.0.1:8090`). Частота ограничена
  на вход (голос — 2 запроса/с, генерация — 20 в минуту) и на адрес; сверх лимита — 429.
  Фронт на 401/429 откатывается на браузерный голос и текст шаблона.
  Проверка: `bash frontend/docker/check-ai-proxy.sh` (поднимает nginx с заглушками изолированно).
  В разработке (`npm run dev`, `vite preview`) то же делает `frontend/dev/aiDevGuard.ts`: вход
  проверяется на бэкенде `VITE_API_TARGET`, наружу те же четыре ручки, но лимитов частоты нет —
  не открывайте dev-сервер в сеть (`vite --host`) при запущенном ИИ-контуре.
- **Порт 8090** опубликован только на `127.0.0.1` (`AI_BIND`). Бэкенд и nginx ходят к ИИ-контуру
  по сети compose.
- **После финала смените демо-пароли** — `admin/admin123` и тестовых учёток `i.ivanov/teacher123`,
  `v.pupkin/student1337` и прочих: они опубликованы в этом README. Меняйте в кабинете администратора:
  `SADMIN_PASSWORD` применяется, только пока в БД нет ни одного администратора (созданный так
  администратор при первом входе обязан сменить пароль). `PEPPER` можно сменить лишь
  вместе с новой БД — иначе ни один сохранённый пароль не подойдёт. `POSTGRES_PASSWORD` тоже демо
  (`dds_password` без `.env`, `dds_password_secret` из `.env.example`) и задаётся только при создании
  тома `pgdata`.
- **Порты 8080 и 5432** тоже опубликованы только на `127.0.0.1` (`BACKEND_BIND`, `POSTGRES_BIND`):
  фронт ходит к API через nginx, бэкенд к БД — по сети compose. Открыть наружу — `BACKEND_BIND=0.0.0.0`
  в `.env` (нужно, если к этому бэкенду ходит Vite dev с другой машины, например Raspberry Pi
  в Tailscale); БД наружу открывать не нужно.
